C2 通信现状、企业网络限制与遗留风险

恶意程序与控制服务器之间的通信（C2）有哪些方式，企业在网络层应做哪些限制，做完之后还剩什么风险。给负责企业网络和安全的人看。

案例覆盖至 2026 年 10 月产品文档查阅日 2026-10-07不针对特定公司网络或设备型号

先说结论

C2 正在从攻击者自建的服务器，转向企业已经允许的服务。2025 到 2026 年的公开案例里，Google Calendar、Microsoft 365、Discord、Telegram、Cloudflare Tunnel、Tailscale 和商业远程管理工具都被用作控制通道。

网络层能做三件事：收紧 DNS，阻塞不需要的服务和端口，记录足够的日志供关联分析。这三件事挡得住大部分自建 C2 和地址寻址，也能让隧道和远程管理工具的滥用留下痕迹。

网络层挡不住藏在已允许云服务里的 C2。那部分需要终端进程证据和服务审计日志。企业应把网络限制当成第一层，不当成唯一一层。

本文依据公开的一手报告和产品文档。规则、阈值和次序是建议，需要在各自环境中测试。本文不修改任何网络设置。

第一部分：C2 现状

1.1 C2 由几段通信组成

恶意程序常有几段通信：寻找控制地址、下载下一段程序、交换命令、上传结果、传送文件。一个服务可以承担一段，也可以承担全部。

例如，程序先从公共博客或区块链合约读取地址，再用 HTTPS 连接另一台服务器。博客是地址来源，另一台服务器是命令通道。大文件还可能上传到第三个云存储。4,5

只监测上传的服务，会错过早期控制。只阻塞地址来源，会错过已建立的通道。设计限制时，每一段都要考虑。

1.3 趋势一：自建服务器仍是主体，份额在降

Recorded Future 的 2025 年回顾显示，Cobalt Strike 仍是检测到最多的攻击框架，约占攻击工具 C2 服务器的一半，但份额连续两年下降。Metasploit、Mythic 保持位置，RedGuard、Ligolo、Supershell 增长。AsyncRAT 和 QuasarRAT 继续领跑远程木马。34

同一报告对 2026 年的判断是：变化来自渐进调整，攻击者会继续借用合法工具、服务和 CDN，把恶意流量混进正常流量。34 2026 年上半年的后续报告确认了这个方向：Hive0163 用 AI 生成的 C2 框架 NodeSnake，Interlock RAT 则通过 WebSocket 连接硬编码地址。35

这类自建 C2 是网络限制最能覆盖的部分。已知指标、罕见目的地和连接节律都有效。

1.5 趋势三：隧道、远程管理工具和覆盖网络

Red Canary 的 2026 年检测报告分析了超过 11 万起威胁。它把 RMM 列为 2025 年最常见的载荷之一，尤其是在诱导用户粘贴命令的攻击之后。AnyDesk、QuickAssist、SimpleHelp 出现在勒索软件加密之前。2026 年初，ScreenConnect 和 NetSupport Manager 位列滥用榜首。40,41

2026 年 9 月，Microsoft 报告 Storm-2570 使用多种 RMM，并配合 ngrok 和 Cloudflare Tunnel。22 2026 年 8 月，Microsoft 的 TerminalFix 分析记录了 Python 反向隧道，通过加密 WebSocket 转发 TCP 流量。15

2026 年 9 月，Malwarebytes 报告 Kothamine 使用 tailcat。tailcat 借助 Tailscale 的数据通道，包括 WireGuard、NAT 穿透和 DERP 中继，不走常规的账号控制流程。25

这类通道的特点是：不需要开放入站端口，可以走 TCP 443，而且与企业自己批准的工具共用服务。企业允许 Tailscale 或 AnyDesk，并不等于允许所有同类通道。

1.6 趋势四：地址来源公开化

2025 年，Google 报告朝鲜攻击者采用 EtherHiding，把下一段程序和控制地址写进区块链合约。读取既可以通过 RPC 节点，也可以通过集中式区块浏览器 API。4 这种设计让攻击者不必维护域名。阻塞一组 RPC 域名后，攻击者换提供商或换链即可。

MITRE 把这类方式归为 Dead Drop Resolver。5 公共博客、代码仓库、社交帖子都能充当地址来源。

1.7 跨类别的隐藏手段

  • DGA：程序生成大量域名，寻找可用控制地址。
  • Fast flux：一个域名快速更换 IP 或名称服务器。2025 年 4 月的联合公告把它列为防御缺口。26
  • 动态 DNS：域名随设备地址变化。
  • CDN、Serverless：控制服务藏在正常托管平台后面。
  • Domain fronting：可见名称与实际请求目的地不同。10
  • ECH：加密 ClientHello 中的真实服务器名。外部设备只能看到共享名称。27
  • 多层加密：BRICKSTORM 先建 HTTPS，再升级 WebSocket，再在通道内增加 TLS 并复用多个数据流。即使解密外层，内层仍是密文。16
  • 内容隐写：图片、文本和文件都能藏指令。7,15

合法 CDN 也会更换 IP，低 TTL 不能单独证明 fast flux。ECH 本身不是恶意行为。这些手段抬高了网络层单独判断的难度。

第二部分：企业应在网络上做的限制

2.1 原则

  1. 规则按设备类别分组。员工设备、访客、IoT、服务器、开发设备各有独立规则。
  2. 例外必须指定设备、目的地、负责人和到期时间。
  3. IPv4 与 IPv6 采用相同策略。
  4. 允许规则先于阻塞规则生效。检查已有的“允许所有”规则。
  5. 每条阻塞都记录日志。阻塞而不记录，等于放弃了最便宜的报警信号。
  6. 规则只适用于经过网关的流量。离开办公网络的笔记本，需要设备上的 DNS 过滤或网络代理。

第 1 到 3 条是 DNS 控制。阻塞 853 只能处理常规 DoT 和 DoQ。DoH 走 TCP 443，也可经 HTTP/3 走 UDP 443，任何 HTTPS 服务都能转发 DNS。所以要同时限制外部 53、已知 DoH 服务，并记录设备连接多个解析服务的行为。1,2,3

第 5 条针对 Cloudflare Tunnel。官方文档列出标准连接端口 TCP/UDP 7844。阻塞两者可阻塞标准 cloudflared，不需要阻塞整个 Cloudflare 网络。23 但 ngrok 官方说明其代理可走 TCP 443，所以端口规则不能覆盖所有隧道。24

第 10 条只用于减少加密 UDP 的检测缺口，不是通用 C2 规则。WebSocket、DoH 和 VPN 仍可使用 TCP 443。

对服务器和 IoT，逐步采用目的地允许清单。对工程师的通用电脑，先收集业务基线。只允许 80/443，无法识别借用这两个端口的 C2。

传感器应接收 LAN 侧的双向流量。只监测 WAN，NAT 后容易丢失原设备身份。只镜像网关上联，会漏掉同一交换机内的设备通信。镜像流量不会解密 TLS。采集和分析放在独立设备上。

Red Canary 把应用控制列为治理 RMM 的第一步：批准清单之外的 RMM 一律禁止执行。41 这一步在终端完成，网络只能补充。

C2-04 参考 BRICKSTORM 的多 DoH 检测思路。18 数量和时间窗口需按业务调整。

C2-05 可先用观察条件：10 分钟内，同一设备对同一注册域查询至少 100 个不同子域名，至少一半含超过 40 个字符的标签。它只产生调查信号，低速 DNS C2 不一定触发。不要阻塞全部 TXT，邮件验证需要 TXT。CDN、反垃圾邮件和安全软件也会产生类似流量。8,17

C2-06 可先检查 1 小时内至少 20 次小连接，目的地在近 14 天基线中罕见。再检查间隔规律性和传输大小。定时更新、安全软件和监控程序需要排除。长连接用另一条条件，例如持续 30 分钟且目的地罕见。

不要只按流量大报警，命令通道可以很小。不要只按固定间隔报警，攻击者可以改变间隔。不要把共享 CDN 的 IP 稀有度当成域名稀有度。

报警按“设备＋规则＋目的地”去重，同类事件 15 分钟内合并。高置信事件立即通知值班人，其余进入调查队列。自动隔离只用于已验证的高置信规则。

2.7 日志字段与留存

必须保留：

  • 时间、时区和设备唯一标识。
  • 原始客户端 IP、VLAN 和当时的地址归属。
  • 目标 IP、端口、协议、字节数和连接时长。
  • 查询域名、查询类型、响应码；可用时保留响应地址。
  • 允许或阻塞动作、命中规则、IPS 签名和指标来源。
  • 有终端日志时，保留进程路径、签名和父进程。

MAC 地址不能独自保证稳定身份。DHCP 变化、IPv6 隐私地址和设备代理都影响归因。

先保留 30 天可查询日志，再按容量、调查需要和隐私要求扩展到 90 天。网关自身的记录数上限不能直接换算成天数。采样流量记录适合看趋势，不保证保留每次短连接。

监测日志停止、设备时间偏移和镜像丢包。数据源失效时，产生单独的监测报警。没有报警不等于没有通信。

2.8 部署次序

  1. 核对网关版本、存储和日志导出。用自有测试域名生成允许与阻塞事件，确认接收端能查到设备、域名、动作和规则。
  2. 建立 DNS 控制。指定公司解析器，阻塞其他外部 DNS，处理未批准的加密 DNS。验证 IPv4 与 IPv6 结果一致，内部域名正常。
  3. 阻塞低影响服务。无需求的 RPC、未批准的 7844 隧道、未批准 RMM 和远程访问。每类阻塞都有记录，每个例外都有范围和到期时间。
  4. 收集 7 到 14 天行为基线。标记合法更新、浏览器、机器人、CI 和远程支持。规则先只产生调查事件。减少误报时用具体设备和目的地例外，不整体关闭规则。
  5. 启用通知与响应。高置信命中即时通知，行为异常进入队列，日志中断单独报警。高置信事件建议 5 分钟内送达。

  • Network 应用版本不低于 9.0。区域防火墙（Zone-Based Firewall）从 9.0 开始提供。69

UniFi 做不到的部分

Content Filter 和防火墙的域名匹配都依赖 DNS。设备用自带的 DoH 或直连 IP 时，域名规则不生效，只能靠端口规则、IPS 和行为报警补。Content Filter 单个策略可容纳多少条自定义域名，官方文档未写明，上传 2,000 条以上的清单前先测试，待确认。笔记本离开办公网络后，UniFi 的规则全部失效，需要设备上的 DNS 过滤或网络代理。报警 C2-05、C2-06 需要 Zeek 和 RITA 等外部分析，UniFi 自身不做这类行为评分。

完成配置后，按 2.9 的验收表逐项测试，并确认每类事件都送到了日志接收端。

域名层的部署步骤：

  1. 在 NAS 或一台常开的主机上，用容器运行 AdGuard Home。Pi-hole、Technitium 也可以。
  2. 添加上表的清单网址。ThreatFox 的网址带上自己的 Auth-Key。
  3. 把清单更新间隔设为 1 小时。这个设置以小时为单位。83

  5. 在 UniFi 各网络的 DHCP 设置里，把 DNS 服务器改成这台主机。
  6. 按 2.12 的规则 2 和规则 3，阻塞外部 53 和 853 端口。DNS 过滤器所在的主机要排除在外。
  7. 打开 DNS 过滤器的查询日志，送到 2.7 的日志接收端。

这条路不经过 Content Filter，所以不受它的条目上限和未公开接口影响。代价是解析器成了单点。只部署一台时，它停机会让全网无法解析。部署两台，DHCP 下发两个地址。不要把公共 DNS 设为备用地址，否则清单会被绕过。

IP 层的部署步骤：

  1. 在控制台的 Integrations 页面创建 API key。菜单名称以实际界面为准。
  2. 用容器运行 CrowdSec 和它的 UniFi 组件。可选 cs-unifi-bouncer 或 cs-unifi-bouncer-pro，两者都支持区域防火墙。81,82
  3. 把 Feodo Tracker 和 Spamhaus DROP 设为外部清单。cs-unifi-bouncer-pro 可以按设定间隔拉取纯文本 IP 清单。82
  4. 组件会在控制台里建 IP 组和阻塞策略。建好后检查策略顺序，并打开日志。

UDM 的单个 IP 组最多 10,000 条，其他型号可能不同。cs-unifi-bouncer-pro 超过上限时会自动新建一组。81,82 IP 层只放小而准的清单。几十万条的大清单放在 DNS 层。也有项目通过 SSH 在网关上直接改 ipset，它要靠持久化脚本抵抗固件升级。经控制台接口写入的规则在界面上可见，升级后不丢，优先用这种。

“实时”的边界

清单只收录已被发现并上报的地址。攻击者新建的服务器和域名，在上报前不在任何清单里。拉取比生成更频繁没有收益：ThreatFox 每 5 分钟生成，每 5 分钟拉取已是上限。藏在 Cloudflare、Azure 等大型云服务后面的 C2，域名和 IP 都不能阻塞，见第三部分。这三层挡的是已知的常见恶意软件和复用的 C2 工具。新出现的通道要靠 2.6 的行为报警发现。

部署次序：先开 IPS，约 5 分钟。再部署 DNS 过滤器和 DNS 绕过阻塞，约 1 小时。IP 层最后做，可选。用时是估计值。

不想自己运行 DNS 过滤器时，域名层可以交给托管服务，见 2.14。
